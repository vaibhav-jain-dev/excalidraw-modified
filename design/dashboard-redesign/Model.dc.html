Diagrams as the store of record

The library is not a folder of pictures. A drawing is a place you put something you worked out, and the thing you want back later is usually one box inside it — not the file. So the box is addressable: any rectangle can be marked as a tag, a tag is a node, and the edges between boxes, drawings and tags are the map. The graph is the memory; the diagrams are how you write to it.

The model

A drawing sits in exactly one category and at exactly one path, and carries any number of tags. A box carries any number of tags of its own. That last edge is the one that matters: it is what lets a search land on the part of the picture you meant.

Where each thing lives

SQLite — stays unchanged
  • Drawing metadata: id, path, category id, title, description, timestamps.
  • FTS5 over the title, description and every string drawn inside the diagram.
  • sqlite-vec embeddings for the meaning rung of the search ladder.
  • Version history rows.

Relational, set-shaped, already fast. Nothing here needs to change.

JSON graph store built
  • Nodes: scene, box, tag, category, folder.
  • Edges: tagged, tagged-part, contains, links-to, filed-under, lives-in, child-of.
  • Loaded whole into memory at boot; re-derived per scene on save; flushed as one file.
  • Category and folder are separate axes, both nesting: a slash path becomes a chain joined by child-of.

A recursive-CTE tag walk in SQLite buys nothing at this size and costs a schema migration every time an edge kind is added. The graph is small, read constantly and traversed in every direction — hold it in memory and persist it as plain JSON that a person (and an agent) can read.

graph.json

{
  "version": 1,
  "nodes": {
    "tag:broken-code":     { "kind": "tag",      "label": "broken-code", "created": "2026-03-04" },
    "scene:ingest":        { "kind": "drawing",  "path": "work/local-first", "category": "cat_store" },
    "box:ingest/el_7f21":  { "kind": "box",      "scene": "scene:ingest", "label": "Broken code path" },
    "cat:cat_store":       { "kind": "category", "label": "Storage", "parent": "cat:cat_arch", "archived": false }
  },
  "edges": [
    { "from": "scene:ingest",       "to": "cat:cat_store",     "kind": "filed-under" },
    { "from": "scene:ingest",       "to": "tag:local-first",   "kind": "tagged" },
    { "from": "box:ingest/el_7f21", "to": "tag:broken-code",   "kind": "tagged-part" },
    { "from": "box:ingest/el_7f21", "to": "tag:error-path",    "kind": "tagged-part" },
    { "from": "scene:ingest",       "to": "scene:graph-store", "kind": "links-to" }
  ]
}

Box ids are Excalidraw element ids, which already survive save → load → restore, so a part-tag keeps pointing at the same rectangle across edits. A box that is deleted leaves a dangling edge; the loader drops those on the next boot rather than blocking the save.

Linking one drawing from another

Right-click in the editor gives two ways to write to the graph: Add tag and Link drawing…. The link picker is the ordinary library list with a search box over it — same rows, same thumbnails. Picking one writes a links-to edge and drops a reference on the canvas in one of two shapes.

Title only
  • Renders as a small chip carrying the target's title and an external-link mark.
  • Clicking it opens a preview popup — thumbnail, path, category, slug.
  • Cheap: nothing of the target is rendered until asked for.
Embedded block
  • Renders the target inline, like an image, with a header carrying its title.
  • Marked read-only and it means it: the host drawing can move and resize the block but can never edit what is inside it.
  • The thumbnail is the target's own rendered PNG, so it refreshes when the target is saved.

Either shape can be flipped to the other at any time — the edge does not change, only render. Both carry the target's slug, and opening one is always a new tab at localhost:3056/d/<slug>, never an in-place takeover of the drawing you are in. A link to a drawing that is later deleted keeps the edge and renders as a dead reference rather than vanishing silently.

Saving is not indexing

A save writes one file and returns. Everything derived from it — and there is a lot now — is queued for a background worker, so the editor never waits on an embedding run or a PNG render.

On the request
  • Write scene.excalidraw.
  • Bump the version row.
  • Enqueue index(sceneId) and return.

Single file write, one row, one enqueue. Nothing else.

On the worker
  • Derive scene.md, scene.semantic.json, scene.mmd.
  • Render the square thumbnail.
  • Replace the FTS5 rows, including every string drawn on the canvas.
  • Re-embed changed chunks.
  • Reconcile tag and link edges into graph.json.

One worker, a persisted FIFO queue, jobs coalesced per scene — save five times in ten seconds and the scene is indexed once, against the last state. Every step is idempotent and re-runnable, so a crash mid-job costs a redo and never a corrupt index. The queue survives restart; on boot, anything left pending is picked back up. Until a scene's job drains, its card carries an indexing chip: the drawing is already safe on disk, it is search that is a moment behind.

Thumbnails

A drawing is whatever size it grew to. A thumbnail is always the same fixed square, and the job is to make a board recognisable at 200px without lying about it.

  • Fit, never crop. The scene is scaled down into the square with a small margin. A board ten screens wide zooms out; it does not show its top-left corner at 1:1.
  • Draw the extent. A dashed boundary marks the drawing's real bounds, so a small diagram floating in a big canvas still reads as a small diagram.
  • Best area when fitting would render a speck. When the bounding box is far larger than the area you actually drew on, the thumbnail shows the densest region instead. The heuristic is cheap and needs no render: bucket element bounding boxes into a coarse grid, take the heaviest contiguous window, pad it. O(n) over elements, run inside the same worker job that produces the PNG.
  • Say when it is a detail. Those thumbnails carry a detail chip with a minimap showing which part of the board is in frame. A cropped view never passes for the whole thing.

Opening a drawing

Clicking a card opens the drawing read-only, over the live socket — it renders immediately, follows saves made elsewhere, and takes no write lease. Editing is a deliberate second step behind the Edit button.

  • Read-only is the cheap path: no editor state to build, no lock to take, safe to open from a link or a search result you are only checking.
  • Embedded drawings inside another drawing are the same view, which is why they can never be edited in place.
  • Edit takes the write lease. A second tab that already holds it keeps it; the newcomer stays read-only and says so rather than silently forking the scene.

Derived, except where it cannot be

Every edge above is re-derived from the drawing on every save and on every metadata edit, so the graph cannot drift from what is drawn — which is why a lost graph.json costs a rebuild and never data.

The exception is the reason the graph exists at all. An LLM can look at the rendered image and add what no amount of parsing would find: that a diagram is a state machine, that a scribble is a retry ladder. Those edges are written by: "agent", and they are the one thing a re-derive must not destroy — reconciling skips them, and a rebuild keeps them along with the note attached to each scene.

Derived from the file
  • Tags on the scene and on individual boxes.
  • Category and folder chains.
  • Links to other drawings, with their render mode.
Added by lookingagent
  • Extra tags a person would not have bothered to type.
  • A one-line note on what the drawing shows.
  • Survives saves and rebuilds; clearable in one call.

So the graph is the image's information layer: folder, category, tags, boxes and links derived from the file; meaning added on top by something that can see. describe_scene returns all of it in one read, every tag marked as a person's or a model's.

The search ladder

One query, four passes, results grouped by which pass caught them so the ranking is legible instead of magic.

1
Category path
Matches the whole ancestry, so “storage” finds everything under Architecture → Storage → Graph store.
sqlite · categories
2
Title and description
What you called it when you filed it.
sqlite · fts5
3
Text drawn inside the diagram
Every label, sticky and arrow caption is indexed with the drawing. Search “broken code”, get back the drawings where you wrote it on a box — and the result highlights that box rather than just naming the file.
sqlite · fts5
4
Close in meaning
Embeddings over the same text, for when you remember the idea and not the words. Ties break on recency, then on how many edges the node has.
sqlite-vec + graph

Rules that do not bend

A category id is permanent
Renaming changes the label and nothing else. Every drawing keeps pointing at the same id, so a rename never re-files anything and never breaks a link or a saved filter.
Categories are archived, never deleted
A drawing that points at a category must always resolve. Archiving hides it from the sidebar and the picker; the drawings filed under it keep it and still show it on their cards.
A folder is a path, not a category
Every file knows where it sits on disk and the card shows it. Filtering the library by folder is the one thing deliberately left for later — the path is displayed and indexed now, so nothing has to be re-modelled when it lands.
